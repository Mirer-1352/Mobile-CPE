# 0.10.0 共享可靠性改造

本版为本地验证版，versionCode 26，未发布 GitHub Release。主要改造共享观察、请求结果、恢复策略和诊断边界；不引入 DexKit 或新的 ROOT 传输依赖，原有现代 libxposed API 102 保持不变。

## 实现边界

- `TetheringBackend` 负责 Android/Mainline 能力、接口类型、原生事件与平台信息；`TetheringObservation` 维护线程安全的完整观察快照。回调只更新状态，不向请求通道写入额外回复。
- API 30+ 优先使用原生回调的实际接口集合。首次回调前才回退旧查询；原生空集合不被旧查询的残留接口覆盖。旧字符串回调和新 `TetheringInterface` 集合均可接收。
- 实际接口类型优先于名字猜测；旧回调结合 EthernetManager 的接口名单。NCM 归为用户界面的 USB 共享，原生不支持 RNDIS 但支持 NCM 时选择 NCM。关闭 USB 时，仅在观察到独立 NCM 活跃时补充停止它；Host 模式仍保护外接设备。
- 能力未知与已确认不支持分别处理，不把 SDK 版本当成实际 ROM 能力。Android 9–10 保留旧 ROOT/ResultReceiver 分支，不调用原生以太网共享 API。
- 现代停止请求接收系统结果；从当前 ROM 的生成 Stub 读取回调事务号，不猜测服务事务号。缺少连接器适配入口时回退旧停止调用，后续仍须观察实际关闭。
- `SharingReconciler` 只协调持久期望、实际观察、启动宽限期和退避。异步接口错误保留原生代码、常量名和事件序号；权限/鉴权/不支持与暂时失败分开处理。前者等待用户、硬件、能力或 ROOT 会话变化，同时每五分钟允许低频探测，避免漏掉厂商通知后永不恢复。
- 下游已开启而上游消失时，保留下游，不为了上游切换反复重启热点或网卡。报告包含原生上游、IPv4/IPv6 默认路由存在性、DNS 数量、MTU、VPN 候选和卸载状态，只读，不改变路由或卸载开关。
- 主屏继续保留现有仪表布局、固定 M/s、长按设置及按实际状态变色。等待/失败详情放在设置，开关始终保留用户期望。

## 诊断

MCPE 设置末尾展开「查看诊断」后可「复制诊断报告」。应用私有、设备加密存储以原子文件保存最多 160 条、总计 64 KiB 的结构化事件，进程替换和重启后继续保留。

记录配置意图、ROOT 操作请求/提交/失败、原生错误、接口/上游变化、ROM/SDK/Mainline 版本、ROOT UID/SELinux 上下文，以及 USB 端口、设备 VID/PID/类和驱动绑定。USB 诊断不读序列号或设备显示字符串；报告不收集热点密码、SSID、客户端地址、数据包内容或每秒流量计数。生成报告不调用共享控制。

## Find 以太网故障：仍在定位

用户原始对照为 0.8.1：ROOT+模块后重启故障，停用模块重启仍故障，撤销本应用 ROOT 后重启恢复。本次连入时已是 0.9.0，故障表现为系统没有登记网卡接口。

当前物理设备是**自带网口的一体式扩展坞**。早期暂停共享守护并物理重插后，系统仍只枚举 USB 3.1 Hub；网卡设备、驱动绑定和以太网接口未出现。0.10.0/code25 保留 ROOT 和守护后实际重启，仍未枚举网卡；这次开机的应用日志没有共享开启/关闭请求。此时不能据此判定硬件损坏或认定用户的 ROOT 对照无关。

第二轮保留 ROOT 授权，持久暂停系统守护并强停应用后重启，确认应用没有运行、系统守护暂停且无新应用启动记录，网卡仍未登记。第三轮仅撤销本应用 ROOT 后重启，保持暂停/强停及其他模块状态，初始也没有网卡。随后物理重插，实际枚举出 Realtek `0bda:8153`、`r8152` 驱动、`eth0`、USB2 Hub 与读卡器，与用户补充的恢复现象一致。

从此正常基线恢复本应用 ROOT、重新启动应用并保持守护暂停，配置同步成功后 `eth0` 保留；独立 ROOT 只读观察也未使其消失。恢复共享守护后，仅请求类型 5，原生回调确认 `eth0` 共享、上游为 Wi-Fi，EthernetTracker 进入 mode 2、一个共享请求；没有 USB 共享操作。

最终 code26、ROOT/模块/守护均开启时再次物理重插，通过接口消失→重新枚举→原生共享恢复的对照，所有偏好完整保留。该轮主机首次观察 `eth0` 重新出现至共享确认约 35.5 秒，应用实际提交请求后约 3 秒；接口观察与请求之间的延迟尚未单独定位，不能称为即时恢复。最初未枚举状态的根因尚未证实，不能将当前恢复成功等同于完全修复原始 0.8.1 问题。

补充验收：最后一次整机重启后，用户明确确认扩展坞未拔插即自行恢复。该次启动约 15.7 秒枚举网卡，应用约 20.2 秒启动、22.8 秒首次 ROOT 观察已含 eth0 并提交原生以太网请求，23.7 秒确认共享。ROOT、模块、守护保持开启。这证明该次开机无需拔插；尚不能保证所有启动条件下均恢复，也未据此宣称找到原始 0.8.1 故障根因。后续后台冻结与桌面改动见 [0.10.1 验证](RELIABILITY_0.10.1.md)。

早期内核日志可能被高频厂商日志覆盖，缺少日志不等同没有发生事件。

VPN 出口、IPv4/IPv6 客户端通路、真实网卡共享/重插、Android 9–15 与其他厂商 ROM 仍需对应环境验收。VPN 按用户要求暂不连接测试。
